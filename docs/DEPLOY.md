# DEPLOY — چطور این پروژه روی سرور می‌رود

> **خلاصه‌ی یک خطی:** شما هیچ دستوری روی سرور اجرا نمی‌کنید. کد که به `main` مرج شود، GitHub
> Actions خودش بیلد می‌کند، می‌فرستد، و pm2 را ری‌لود می‌کند.

این فایل قبلاً راهنمای Docker بود و به شما می‌گفت `ssh root@…` بزنید. آن مدل کنار گذاشته شد،
چون سرور **مشترک** است: محصولات درآمدزای دیگری روی همان pm2 و همان دیسک زندگی می‌کنند، و
`PLATFORM.md` برای همین یک قرارداد سخت‌گیرانه دارد. آن قرارداد مرجع است؛ این فایل فقط می‌گوید
«آرایشگر» کجای آن می‌نشیند.

## ۱) چه چیزی کجا می‌نشیند

| چیز             | مقدار                                      | چرا                                                    |
| --------------- | ------------------------------------------ | ------------------------------------------------------ |
| پوشه            | `~/arayeshgar`                             | الگوی سند                                              |
| اپ‌های pm2      | `arayeshgar-web` · `arayeshgar-bots`       | پیشوند دارند تا با اپ هیچ محصول دیگری تصادم نکنند      |
| پورت وب         | `127.0.0.1:8800`                           | `8787` اشغال داشبورد است؛ و هیچ پورتی روی اینترنت نیست |
| دیتابیس         | `~/arayeshgar/data/arayeshgar.db`          | مسیری که بکاپ شبانه و داشبورد مشترک انتظار دارند       |
| آپلودها         | `~/arayeshgar/data/uploads/`               | همراه بکاپ دیتابیس نیست؛ جدا tar می‌شود                |
| دسترسی از بیرون | تونل نام‌دار کلادفلر (`arayeshgar-tunnel`) | آدرس ثابت بدون باز کردن هیچ پورتی                      |

## ۲) چرا روی سرور هیچ چیزی نصب نمی‌شود

الگوی `PLATFORM.md` روی سرور `npm ci --omit=dev` می‌زند. برای ما کار نمی‌کند، به دو دلیل: این
یک مونوریپوی pnpm است و pnpm روی سرور نیست، و قاعده‌ی ۸ می‌گوید سرور ممکن است اصلاً به registry
نرسد. پس **همه‌ی بیلد روی رانر انجام می‌شود** و چیزی که به سرور می‌رسد خودکفاست:

| اپ   | چطور بیلد می‌شود                       | خروجی                              |
| ---- | -------------------------------------- | ---------------------------------- |
| web  | `next build` با `output: "standalone"` | `web/server.js` + وابستگی‌های لازم |
| bots | `node apps/bots/build.mjs` (esbuild)   | `bots/index.js` — یک فایل          |

**تنها استثنا:** `@libsql/client` و `libsql` باندل نمی‌شوند، چون `libsql` یک باینری کامپایل‌شده
(`.node`) لود می‌کند. این دو باید به‌صورت فایل واقعی کنار باندل فرستاده شوند، و اینکه کدام
باینری پیش‌ساخته درست است به نسخه‌ی Node و پلتفرم سرور بستگی دارد — که با `Ops → status`
مشخص می‌شود و در `deploy.yml` قفل می‌گردد. تا آن موقع حدس نمی‌زنیم.

## ۳) مهاجرت‌های دیتابیس

`pnpm db:migrate` از `packages/db/src/migrate-cli.ts` می‌گذرد. فایل‌های `.sql` پیش‌فرض کنار
همان پکیج پیدا می‌شوند، ولی در یک بیلد جابجاشده چنین پوشه‌ای وجود ندارد — پس متغیر
`MIGRATIONS_DIR` هست تا دیپلوی به جایی که واقعاً فرستاده اشاره کند.

مهاجرت‌ها فقط **افزایشی**اند (بند ۱۵-۳): `ADD COLUMN` با `DEFAULT`، هرگز `DROP` یا `RENAME`.
دلیلش ساده است: دیپلوی و اپ قدیمی برای چند ثانیه هم‌زمان زنده‌اند.

## ۴) کاری که فقط شما می‌توانید بکنید

همه‌اش در `Settings → Secrets and variables → Actions` است و هیچ‌کدام ترمینال لازم ندارد.
جدول کامل در `CLAUDE.md` بند ۳ است. **الان یک قلم مسدودکننده است:**

`VPS_SSH_KEY` باید همان کلیدی باشد که در ریپوی مونوریپو کار می‌کند. `Ops → ssh-check` ثابت کرد
کلید فعلی سالم، کامل و بدون رمز است (RSA‑2048) و پورت ۲۲ باز است، ولی سرور آن را نمی‌شناسد:
`Permission denied (publickey)`. تا این عوض نشود هیچ دیپلویی ممکن نیست.

## ۵) وقتی چیزی خراب شد

هیچ‌وقت SSH نمی‌زنید. ورک‌فلوی `Ops` (دستی، از تب Actions) این‌ها را دارد:

| اکشن                    | چه می‌گوید                                 |
| ----------------------- | ------------------------------------------ |
| `status`                | اپ‌ها online‌اند؟ نسخه‌ی Node؟ دیسک؟       |
| `logs` / `errors`       | آخرین خطوط لاگ / فقط خطاها                 |
| `restart`               | فقط اپ‌های خودِ آرایشگر، نه اپ دیگری       |
| `env-check`             | کدام متغیر ست است — **مقدارش چاپ نمی‌شود** |
| `db-query`              | یک `SELECT` — فقط‌خواندنی                  |
| `admin-add/remove/list` | مدیریت ادمین‌های پلتفرم با آی‌دی عددی      |
| `ssh-check`             | تشخیص اتصال، روی خودِ رانر                 |

جدول علائم و کار متناظرش در `docs/RUNBOOK.md` است.

## ۶) چیزی که هنوز ساخته نشده

`deploy.yml` **عمداً** هنوز نوشته نشده. اولین مرج به `main` بعد از ساختنش یک دیپلوی واقعی روی
سروری است که محصولات دیگرتان آنجاست، و `PLATFORM.md` می‌خواهد اول با `Ops → status` تأیید شود
که نه نام `arayeshgar-web`/`arayeshgar-bots` با اپی تصادم دارد و نه پورت `8800` اشغال است.
آن هم به همان کلید SSH بند ۴ بند است. `health.yml`، `backup.yml`، `tools/manual-deploy.sh` و
سرویس تونل کلادفلر هم پشت همین منتظرند.
